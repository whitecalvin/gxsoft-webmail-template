# GXWebMail ↔ TASTEMAIL 기능 계약 및 미지원 목록

알림 경계: live 헤더의 알림 버튼은 위치를 유지하지만, TASTEMAIL 사용자 알림 피드/읽음 API가 확인되지 않아 시연용 결재·멘션 알림, 읽음 처리, 알림 센터 링크를 표시하지 않는다. 대신 서버 알림이 미연동임을 명시한다. mock 모드의 기존 알림 시연은 유지한다.

발송 거절 후 초안 경계: 서버가 `EmailSubmission/set.notCreated`로 발송을 명시적으로 거절하면 GXWebMail은 해당 시도에서 새로 생성한 임시 초안만 삭제한다. 삭제가 확인된 경우 기존 오류 상태를 보여주고 수정·재시도를 허용한다. 삭제가 확인되지 않으면 중복 초안을 피하도록 재시도를 잠그고 임시보관함 확인을 안내한다. 사용자가 편집하던 이전 초안은 이 정리 대상으로 삼지 않는다. 실제 계정의 발송 거절·초안 정리 결과는 아직 검증하지 않았다.

임시보관 메일 재편집 메모: live 일반 텍스트 초안은 수신자·제목·본문·첨부·답장 참조 헤더를 작성 창에 다시 채운다. Rust JMAP은 초안 본문 변경을 `Email/set.update`로 지원하지 않아, 저장 시 새 초안을 만든 다음 이전 초안을 삭제한다. 서버는 삭제 전 개인 계정의 `$draft`와 Drafts 메일함 소속을 확인하며, 새 초안 저장 또는 발송이 확정되기 전에는 이전 초안을 삭제하지 않는다. 삭제 결과가 확인되지 않으면 성공 안내와 함께 이전 초안이 남을 수 있음을 표시한다. 기본 발신자와 다른 주소의 초안도 현재 `Identity/get`과 사용자 발신자 설정에 남아 있으면 원래 발신자를 유지하며, 삭제·비활성화된 발신자는 저장·발송하지 않는다. HTML 초안은 서식 손실을 피하려고 현재 읽기 전용이다. 실제 계정의 재편집·발송·이전 초안 정리 결과는 아직 검증하지 않았다.

답장·전달 연결 메모: live 메일 상세의 답장·전체 답장·전달 작성 창을 활성화했다. `Email/get`의 `replyTo`를 회신 주소로 우선 사용하고, 내가 보낸 메일은 다른 원래 수신자에게 답장한다. `messageId`·`references`는 답장 초안의 `inReplyTo`·`references`로 전달하고, 전체 답장 제출에서는 서버가 반환한 사용 가능 발신 주소(별칭 포함)를 자기 수신에서 제외한다. 전달은 원본 본문을 인용하고 기존 첨부의 `m:{messageId}:{index}` blob을 새 초안에 참조한다. 20개를 넘는 첨부가 있는 메일은 전달 버튼을 비활성화한다. Rust JMAP 계약은 소스로 확인했으나 실제 계정의 초안·발송·첨부 보존 결과는 아직 검증하지 않았다.

격리 구현 메모: live 화면은 관리자 전용 `POST /api/admin/quarantine/{id}/release`(`target: inbox`)와 `POST /api/admin/quarantine/{id}/discard`를 같은 출처의 Next.js 경유로 연결했다. 해제·영구 삭제는 확인 대화상자를 거치고, 성공 응답의 ID·상태가 일치할 때만 완료로 표시한다. 응답 중단·5xx·파싱 실패는 처리 결과 불명으로 안내하고 자동 재요청하지 않는다. 일괄 처리는 미연동이고 실제 관리자 계정의 변경 결과는 검증하지 않았다.

첨부 파일 화면 구현 메모: live 모드는 더 이상 시연용 파일·용량·대용량 링크를 표시하지 않는다. JMAP `Email/query`의 `hasAttachment`, `attachmentName`, `from` 조건과 `Email/get`의 첨부 메타데이터를 사용해 실제 메일 첨부를 페이지 단위로 표시하고, 인증된 다운로드 프록시로 받는다. 페이지 수는 **첨부 개수가 아닌 메일 개수**를 기준으로 한다. 독립 파일 저장소·공유 링크·첨부만 삭제하는 정리 기능은 서버 계약이 없어 live 화면에 표시하지 않는다. 실제 계정에서의 파일 검색·다운로드는 아직 검증하지 않았다.

캘린더 구현 메모: 새 일정에는 참석자 이메일을 최대 100개까지 입력할 수 있으며 서버의 `attendeeUsernames` 계약으로 전달한다. 서버는 초대장을 발송할 수 있으므로 화면에 외부 효과를 미리 알린다. 참석자가 있는 일정의 취소는 현재 revision을 확인한 뒤 서버에 전달하며 서버가 취소 알림을 처리한다. 참석자가 있는 일정의 수정은 기존 참석자 목록이 빈 목록으로 대체될 위험 때문에 여전히 비활성화한다. 합성 사례는 작성했지만 변경된 앱에 대해 실행하지 않았고 실제 계정의 초대 발송도 검증하지 않았다.

메일 이동 구현 메모: 개인 메일의 시스템 편지함(inbox/drafts/sent/archive/junk/trash) 소속만 대상 역할로 이동하며, 사용자 지정 편지함 소속은 보존한다. `Email/get`의 계정 상태를 `Email/set.ifInState`에 전달해 변경된 상태를 감지하고, 상태 불일치·응답 실패 시 UI 목록을 다시 읽어 결과를 확인한다. 합성 API 사례는 추가했지만 실행하지 않았고 실제 계정에서의 이동 결과는 검증하지 않았다.

설정 화면 경계: live 모드의 필터 설정은 TASTEMAIL 메일 규칙 API를 사용한다. 그 밖의 서버 계약이 연결되지 않은 설정 세부 화면에는 시연용 안내를 표시하며, 화면 조작이 서버 계정 설정 변경으로 보이지 않게 한다. 언어·테마·접근성·단축키는 브라우저 로컬 설정으로 유지한다.

가입 화면 경계: live 로그인 화면에서는 시연용 가입·설치 마법사 링크를 표시하지 않는다. live `/signup`에 직접 진입해도 계정 생성 폼과 가짜 성공 흐름 대신 관리자 계정 발급 안내와 로그인 링크만 표시한다. mock 모드의 가입 시연 흐름은 유지한다. Rust 소스에 사용자 셀프 가입 계약이 확인되기 전까지 live 계정 생성으로 표시하지 않는다.

설치 화면 경계: live `/setup`은 TASTEMAIL 설치 패키지의 `TASTEMAIL_INITIAL_SETUP_CONFIG`, `TASTEMAIL_INITIAL_SETUP_REQUEST`, `TASTEMAIL_INITIAL_SETUP_STATUS`, `TASTEMAIL_INITIAL_SETUP_TOKEN` 경로가 모두 Next.js 서버에 설정된 경우에만 최초 설치 마법사를 제공한다. 일회용 설치 토큰을 확인하고, `TASTEMAIL_INITIAL_SETUP_V6` 요청 파일을 원자적으로 생성하여 패키지의 설치 서비스에 전달한다. 화면은 상태 파일을 읽어 대기·진행·오류·완료를 표시한다. 이 환경 계약이 없는 개발 서버에서는 설치 불가 안내를 표시한다. 일반 Rust `7531` API만으로는 패키지 최초 설치를 실행할 수 없다. mock 모드의 7단계 설치 시연은 유지한다. 실제 패키지 설치와 완료 후 로그인은 아직 검증하지 않았다.

관리자 화면 경계: `/admin`, `/admin/onboarding`, `/admin/system`은 현재 mock 데이터와 시연 동작을 사용한다. 공통 관리자 레이아웃에서 live 모드에는 세 화면을 렌더링하지 않고 미연동 안내를 표시한다. mock 모드의 관리자 콘솔과 전용 레이아웃은 유지한다. Rust의 실제 관리자 API가 일부 존재하더라도 시연 UI 전체가 연결된 것은 아니므로 실제 관리자 데이터나 변경 결과로 오인하지 않게 한다.

세션 구현 메모: 브라우저가 HTTPS로 접속한 요청은 Next.js가 개발 모드여도 HttpOnly 세션 쿠키에 `Secure`를 설정한다. live 로그인 화면은 HTTPS 또는 로컬 loopback HTTP에서만 제출하고, 세션 POST 경로는 같은 출처 `Origin`을 요구하며 요청 본문을 읽기 전에 원격 평문 HTTP를 거부한다. 프록시의 `Host`/`X-Forwarded-Proto` 전달과 HTTPS 종단 설정은 배포 측에서 확인해야 하며, 이 검사만으로 이미 전송된 평문 자격 증명을 보호할 수 없다. 세션 확인 중 Rust API가 401을 반환하면 로컬 세션 쿠키를 삭제하고, 401·403·429·일시적 서버 오류를 구분해 전달한다. 합성 API 사례를 추가했지만 실행하지 않았고 실제 계정 세션 만료는 검증하지 않았다.

로그아웃 구현 메모: Rust `DELETE /api/auth/session`의 204(또는 이미 유효하지 않은 401)에서만 서버 세션 폐기를 확인된 것으로 표시한다. 그 밖의 응답·연결 오류에서는 로컬 HttpOnly 쿠키를 삭제하되 `signout_unconfirmed`로 구분하고, 사용자에게 서버 세션 폐기 미확인을 알린다. Next.js 경로 자체에 요청이 닿지 않으면 로그인 화면으로 이동하지 않고 재시도를 안내한다. 실제 계정의 세션 폐기 결과는 아직 검증하지 않았다.

보안 화면 구현 메모: live `/security`는 Rust의 `GET /api/user/security`에서 TOTP 상태·남은 복구 코드 수·로그인 세션·보안 이벤트를 읽어 표시한다. API 변환 계층은 이벤트의 임의 `detail` 필드를 브라우저로 전달하지 않는다. 확인 대화상자 뒤에 `DELETE /api/user/security/sessions/{session_id}` 또는 `DELETE /api/user/security/sessions`로 다른 기기 세션을 해제하며, 현재 세션은 Rust가 거부하고 UI에서도 대상으로 내놓지 않는다. 성공 응답 후에만 완료를 알리고 실패·응답 불명확 시 목록을 다시 읽는다. mock 보안 점수·가짜 기기/이벤트·가짜 MFA 재발급 동작은 live에서 표시하지 않는다. 그 밖의 실제 보안 설정 변경은 미연동이며, 실제 계정 응답과 세션 해제 결과는 검증하지 않았다.

서명 설정 구현 메모: live `/settings/signature`는 Rust `GET/PATCH /api/user/preferences`의 `identities`와 발신자별 `mailSignature`·`mailSignatureHtml`·`mailSignatureFormat`을 사용한다. mock의 다중 서명 목록과 자동 적용 스위치를 서버 기능으로 오인하지 않도록 별도 화면으로 분리했다. 새 일반 텍스트 작성 창에는 기본 발신자의 텍스트 서명을 로드 후 적용하고, 기존 본문이나 사용자가 먼저 입력한 글은 덮어쓰지 않는다. 서버는 HTML 서명을 정화하여 저장하지만 GXWebMail의 live 작성은 여전히 일반 텍스트만 지원한다. 실제 계정 저장·발송 연계는 검증하지 않았다.

임시저장 오류 경계: `Email/set` 초안 생성 요청 뒤 응답이 끊기거나 생성 결과가 불명확하면 `draft_uncertain`으로 표시한다. 브라우저의 임시저장 요청도 30초 제한 시간을 두고, 네트워크·응답 파싱 실패는 생성 여부 불명으로 처리한다. 작성 창은 같은 내용을 다시 저장하거나 발송하지 않도록 잠그고 임시보관함 확인을 안내한다. 명시적인 `notCreated` 응답은 생성 실패로 구분한다. 실제 계정의 초안 저장·응답 중단 사례는 검증하지 않았다.

작성·첨부 업로드 경계: Next.js의 작성 POST와 업로드 POST는 같은 출처 `Origin`이 없는 요청을 거부한다. 브라우저 업로드에는 120초 제한 시간을 적용하고, Next.js에서 Rust 업로드 요청에는 별도로 60초 제한 시간을 둔다. 업로드 시간 초과는 메일 발송 성공으로 표시하지 않으며, 실제 계정의 업로드·발송 결과는 검증하지 않았다.

받는 사람 자동완성 경계: live 작성 창은 인증된 Next.js 경로를 통해 Rust `GET /api/contacts/suggestions`에 검색어와 최대 8건 제한을 전달한다. 추천 응답은 계정 범위의 저장 연락처와 사용 이력을 포함하며, 선택 시 이메일 주소만 수신자로 추가한다. mock 작성 창은 API를 호출하지 않는다. 실제 계정의 추천 결과와 키보드·터치 선택은 아직 검증하지 않았다.

기준: 2026-09-28의 `tastedev-mail` 소스(`crates/tastemail-api/src`, `apps/webmail/src`)와 GXWebMail의 현재 mock 화면. 아래의 **소스 지원**은 Rust 소스에 경로·메서드가 있다는 뜻이며, 실제 계정으로 요청이 성공했는지는 아직 검증하지 않았다.

## 연결 확인 상태

- Rust 소스에는 무인증 `GET /health`, 인증 `POST/DELETE /api/auth/session`, 인증 JMAP `GET /.well-known/jmap`와 `POST /jmap/api`가 있다.
- 배포 주소 `http://192.168.0.109:7531`에서 무인증 `GET /health`는 HTTP 200과 `{"status":"ok","service":"tastedev-mail"}`를 반환했고, 무인증 `GET /.well-known/jmap`는 HTTP 401을 반환했다. 이는 네트워크 연결과 인증 경계만 확인하며 실제 계정 로그인이나 배포 소스 버전 일치는 증명하지 않는다.
- 같은 포트의 `https://192.168.0.109:7531/health`는 TLS 프레임 오류로 연결되지 않았다. 현재 확인된 LAN 경로는 평문 HTTP이므로 로그인·토큰 요청에는 사용하지 않는다.
- 소스의 `config/tastedev-mail.toml`과 Linux Web Mail 서비스는 `http://127.0.0.1:7531`을 사용한다. GXWebMail live 모드의 서버 전용 API 기본 주소도 동일하며, **Next.js 프로세스가 실행되는 호스트**의 loopback을 가리킨다.
- live 로그인은 `/health` 응답을 선행 조건으로 삼지 않고, 같은 출처의 `/api/mail/session`으로 인증을 시도한 결과를 표시한다. 무인증 `/api/mail/health`는 선택적 진단 경로이며 실제 계정 인증 성공의 증거가 아니다.
- Rust API 라우터에 `GET /api/auth/session`은 없다. 현재 세션 검사는 토큰을 사용한 JMAP 세션 조회 등 실제로 제공되는 인증 경로를 사용해야 한다.
- 비밀번호와 bearer token은 평문 LAN 경로로 보내지 않는다. 현재 개발 구성은 서버 측 loopback 주소를 사용한다.
- 개발 도메인 `https://webmail-test.gxsoft.co.kr`은 2026-09-28에 DNS A 레코드가 `221.151.221.23`으로 조회되었으나, 무인증 `GET /`, `/ko`, `/ko/login`이 모두 HTTP 500을 반환했다. 응답에는 Next.js의 locale 쿠키와 라우팅 헤더가 있어 요청이 앱 계층에 도달한 것으로 보이지만, 원인은 서버 로그 없이 확정할 수 없다. 저장소의 `deploy/nginx/webmail-test.gxsoft.co.kr.conf`는 배포용 설정안이며 실제 서버에 적용되었다는 증거는 없다. 이 상태에서는 실제 계정 로그인을 검증하지 않는다.

## 미지원 또는 별도 계약이 확인되지 않은 GXWebMail 기능

이 표의 항목은 **현재 확인한 Rust API 라우터와 기존 TASTEMAIL Web Mail 사용 경로에 직접 대응하는 계약이 없음**을 뜻한다. 서버 전체에서 영구적으로 불가능하다는 단정은 아니며, 배포 API가 연결되면 다시 확인한다. live 모드에서는 연결 기능인 것처럼 mock 결과를 조용히 보여주지 않는다.

| 화면·기능 | 현재 판단 | 처리 방향 |
| --- | --- | --- |

| 조직도·부서 트리·구성원 프로필 | 연락처·관리자 그룹 API는 있으나 화면의 조직도 전체 구조 계약 미확인 | mock 전용 유지 또는 조직 디렉터리 계약 설계 |
| AI 일정 감지 제안, AI 문장 다듬기 | 대응 AI API 미확인 | 시연 기능으로 표기하고 live에서 별도 서비스 필요 |
| 회의실 예약 현황·리소스 캘린더 | 일정 API는 있으나 회의실 가용성/예약 계약 미확인 | mock 전용으로 구분 |

| 회원가입·셀프서비스 계정 생성 | 사용자용 signup API 미확인; 관리자 사용자 생성과 다름 | live에서는 별도 정책 결정 전까지 비활성화 |

| 관리자 마이그레이션·백업 실행 데모 | 운영 상태·증거 API와 실제 작업 실행 계약을 혼동할 수 있음 | 운영 API별로 재조사하고 실행 버튼은 연결 전 비활성화 |

## 다음 확인 게이트

발송 경로는 개인 계정의 기본 발신 ID와 첨부 제한을 JMAP 세션·사용자 환경설정에서 확인한다. 초안 생성 후 제출 응답이 끊기거나 불명확하면 중복 제출을 피하도록 작성 창의 보내기 동작을 잠그고, 보낸편지함·임시보관함을 확인하도록 안내한다. 이 보호는 실제 발송 성공을 증명하지 않는다. 배포 서버의 승인된 테스트 계정과 대상이 정해지기 전에는 발송·첨부 업로드를 실제 서버에 요청하지 않는다.

## 현재 구현 상태

- 개인 메일: 서버 전용 인증·JMAP 변환 계층, 개인 편지함·목록·본문·검색·첨부 다운로드를 연결했다. 역할 없는 사용자 지정 편지함은 목록과 검색 필터에서 현재 계정의 ID를 대조해 조회한다. 읽음·별표 및 시스템 편지함 간 이동은 서버 응답 후 목록을 다시 읽는다. 사용자 지정 편지함 생성·이름 변경·삭제·대상 이동은 미연동이다.
- 작성: 일반 텍스트 작성, 명시적 임시저장, 초안 재편집, 첨부 업로드, 발송 큐 제출을 소스 계약에 맞춰 연결했다. 제출 결과가 불명확할 때 자동 재시도하지 않는다. 개인 메일의 영구 삭제, HTML 서식 작성, 예약 발송은 미연동이다.
- 다른 업무: 개인 주소록 조회·추가·편집·삭제, 월별 일정 조회와 본인 일정 변경·참석 응답·참석자 초대 생성, 결재 요청·승인·반려, 메일 규칙 조회·편집·문법 검사·미리보기, 관리자 권한의 격리 조회·해제·삭제를 연결했다. AI 제안·조직도·회의실 현황 등 서버 계약 없는 시연 기능은 live 결과로 표시하지 않는다.
- 공용 편지함: 서버 목록과 JMAP 세션의 공유 계정 읽기 권한을 확인해 편지함·메일·첨부를 읽는다. 공용 읽음 변경·발송·권한 편집은 미연동이다. HTML 본문은 Rust가 정화한 값을 sandbox iframe과 차단형 CSP로 격리해 표시한다.
- 검증 범위: 위 연동은 소스 계약과 정적 검사 중심으로 구현했다. 합성 검증 스크립트의 일부 사례는 작성됐지만 변경된 앱에 대해 전체 실행하지 않았다. 배포 계정의 로그인·읽기·변경·발송 결과, 모바일·데스크톱 회귀는 아직 검증하지 않았다. mock 모드는 독립적으로 유지한다.

사이드바 저장 용량은 mock 모드에서는 시연 수치를 사용한다. live 모드에서는 JMAP `Mailbox/get`의 `x-tastemail-usedBytes`와 `x-tastemail-quotaBytes`가 유효할 때만 표시하며, 서버가 값을 주지 않으면 임의 수치로 대체하지 않는다.

개인 계정의 역할 없는 사용자 지정 편지함은 live 사이드바에 서버 이름·읽지 않은 수와 함께 표시하며, 선택 시 서버가 반환한 편지함 ID에 한정해 `Email/query`·`Email/get`으로 목록을 읽는다. live 검색의 편지함 필터에서도 이 ID를 선택할 수 있으며, 서버는 현재 개인 계정의 역할 없는 편지함인지 다시 확인한다. 사용자 지정 편지함 생성·이름 변경·삭제 및 해당 편지함으로의 이동은 아직 프런트엔드에 연결하지 않았다. 시스템 편지함으로 이동할 때 기존 사용자 지정 편지함 소속은 보존된다. 실제 배포 계정으로 사용자 지정 편지함을 검증하지 않았다.

메일 외 업무 화면으로 직접 진입해도 live 사이드바의 메일함 수치가 비어 있지 않도록, `/api/mail/mailboxes`가 인증된 JMAP 세션과 `Mailbox/get`의 요약만 조회한다. 이 경로는 메일 본문을 읽지 않으며 세션 만료·권한 부족·요청 제한·서버 장애를 구분해 사이드바 오류와 재시도에 전달한다. 실제 배포 계정에서는 아직 검증하지 않았다.

live 전역 검색은 검색어가 없을 때 `Email/query`의 전체 메일 결과를 페이지 단위로 표시하고, 검색어가 있으면 JMAP `text` 조건과 날짜순 페이지 이동을 연결한다. `from:`, `subject:`, `filename:`, `in:`, `has:attachment` 검색 문법은 Rust 서버의 `Email/query` 필터로 변환하고, 따옴표로 묶은 단일 문구에서는 따옴표를 제거한 검색어를 전달한다. 화면의 기간·편지함·첨부 있음 필터도 `after`·`inMailbox`·`hasAttachment` 조건으로 서버에 전달한다. mock 검색 화면의 사람·독립 파일 결과와 첨부 유형·라벨 필터는 여전히 live 화면에 적용되지 않는다. Rust 서버에는 더 다양한 `Email/query` 필터가 있으므로 이는 **서버 미지원**이 아니라 **프런트엔드 미연동**이다.

검색 필터 한도: Rust `Email/query`는 필터 노드 64개와 검색 텍스트 256자를 제한한다. GXWebMail은 화면 필터에 필요한 노드를 남겨 두고 문법 조건 56개 초과 또는 제어 문자 포함 검색을 `400 invalid_request`로 구분한다. 조건이 많은 검색식을 조용히 일반 텍스트 검색으로 바꾸지 않는다.

로그인·메일 읽기·검색의 live 응답은 인증 실패(401), 권한 부족(403), 요청 제한(429), 일시적 서버 장애(5xx)를 서로 다른 상태로 전달한다. JMAP 메서드 응답 자체가 오류인 경우 Rust 소스의 `forbidden`·`accountNotFound`를 권한 부족, `rateLimit`을 요청 제한, `serverFail`을 재시도 가능한 장애로 구분한다. `Email/set`의 개별 `notUpdated`에서도 `serverFail`을 재시도 가능한 장애로 전달한다. 합성 루프백 사례는 작성됐지만 변경된 앱에 대해 전체 실행하지 않았고 실제 배포 서버의 정책·제한값도 검증하지 않았다. 메일 로드 실패 시 이전 목록·용량·읽지 않음 수를 현재 결과처럼 표시하지 않는다.

1. GXWebMail Next.js를 API와 같은 호스트에서 실행해 서버 전용 `127.0.0.1:7531` 경로를 사용하거나, 인증 정보를 보호하는 별도 전송 경로를 확정한다. LAN의 평문 HTTP 경로로 로그인·토큰 요청을 보내지 않는다.
2. 배포 버전이 조사한 소스와 일치하는지 확인한다.
3. 테스트 계정이 준비되면 MFA, JMAP 세션, 읽기 전용 메일함·목록·상세를 순서대로 검증한다.
4. 기능마다 `지원/미지원/권한 필요/배포 미확인` 상태를 갱신한다. 변경·발송 API는 그 뒤 별도로 검증한다.
