[최신 연결·검수 범위](linked-job-control-server-request-20261013.md).

## 최신 확인 — 2026-10-13

- 현재 runtime은 live-only다. 아래 날짜별 mock 유지·가입 시연·localStorage 일반 설정 설명은 이전 이력이며 실행 방법으로 사용하지 않는다. README의 현재 route·설정 안내를 소스와 대조해 정리했다. 메일 규칙의 canonical 주소는 `/settings/rules`이며 `/rules`와 이전 `/settings/filters`는 리디렉션한다.
- 사용자 확인을 포함해 현재 IARC 메일의 이미지 표시 문제가 해결됐다. 특정 메일의 표시 성공이며 모든 발신자·브라우저의 이미지 수용을 뜻하지 않는다.
- 관리자 원격 관리의 초기 `management_not_configured` 응답은 이전 관측이다. 이후 서버 채팅에서 별도 운영 승인으로 구성을 완료했고, 인증된 프런트엔드에서 네트워크·노드·업데이트 관리 가능, 최신 버전 0.1.39, 자동 설치 OFF와 번역된 작업 이력을 확인했다. 서버 보고서는 전용 Ed25519 feed·패키지/baseline 검증과 기존 타이머의 후속 실행을 기록한다. 실제 설치·롤백·역할/네트워크 변경의 수용, 향후 릴리스 자동 feed 발행은 이 결과에 포함되지 않는다. [현재 관리자 검증](TASTEMAIL_ADMIN_IMPLEMENTATION.md).
- 변경된 프런트엔드의 기본 Turbopack 빌드(410페이지)는 새 검증 디렉터리에서 성공했다. 관리자 합성 BFF 검증 및 현재 화면 관찰과 실제 특권 작업 실행은 별개다. [상세 검증](TASTEMAIL_ADMIN_IMPLEMENTATION.md)을 따른다.
- 현재 계정별 일반 설정 Provider는 서버 snapshot·revision/receipt를 사용한다. 외부 이미지 표시 정책과 발신자 허용 설정도 이 저장 경로에 연결돼 있다. 아래의 브라우저 로컬 저장 설명은 당시 이력이다. 전체 계정 격리·장애·세션 만료와 실서버 저장 수용을 소스 연결만으로 완료 처리하지 않는다.
- 전체 연동의 실수용은 아직 미완료다. 승인된 현재 세션의 실제120초 만료·로그인 전환·시험 설정 원복은 [실제 만료 기록](session-expiry-live-20261013.md)에서 확인했다. 추가 로그인 만료 안내는10언어 운영 HTTP와 격리 화면으로 검증했다. 다른 MFA·권한/복구 조합, 외부 계정 인증·동기화 워커, 승인된 운영 변경·외부 발송 및 전체 다국어/모바일 검증은 개별 대상·권한과 증거가 필요하다. 주소록1명 조회/검색과 빈 캘린더·공용 목록의 [읽기 검수](auxiliary-readonly-20261013.md)는 실제 항목·공유 권한 수용을 대체하지 않는다.

## 현재 실행 계약과 기록 해석 — 2026-10-08

- 2026-10-10 최신 인증된 검증: 기존 계정의 접근성 설정을 10개 언어에서 desktop1280px/mobile390×844px로 조회했다. 사용자 승인으로 글자 크기100%→110% 저장 성공을 확인했고 새로고침 후110%/HTML scale1.1 유지, 원래100% 복원·저장 후 새로고침에서100%/scale1/저장됨 유지까지 확인했다. 아래 API 미지원·운영 저장 미검증은 그 이전 이력이다. 직접 DB 조회, 전체 설정의 영속성, 계정 전환/격리, MFA·세션 만료·권한 거부·장애 복구 및 전체 제품 GUI는 이 결과로 완료 처리하지 않는다. - 2026-10-10 운영 후속: 서버 세션은 109 API0.1.31·DB0064 적용과 일반 설정 API401 인증 요구를 보고했다. 아래 운영 배포 대기 문구는 이전 관측 이력이다. 인증된 일반 설정 GET/SSR·실제 계정 저장/영속성·모바일 QA는 여전히 미검증이다. 로컬 안전 연결 복구 후 사용자의 종료 요청으로 웹메일7540/SSH터널16711을 종료했으며 자동 재시작하지 않는다. [최신 체크포인트](general-settings-integration-checkpoint-20261010.md)를 따른다.

[일반 설정 구현·검수 체크포인트](general-settings-integration-checkpoint-20261010.md), [실제 서버 미지원 화면 및 모바일 제한](general-settings-browser-qa-20261010.md)을 따른다.

- 최신 폴더/편지함 구분·아이콘 미리보기/적용·포인터 이동 및 실패한 테스트 게이트 재개 결과는 [사이드바 상호작용 검증](SIDEBAR_INTERACTION_VERIFICATION_20261008.md)을 따른다. 로컬 재개 합계와 실제 브라우저/서버 검증은 구분한다.
- 사용자의 후속 mock 완전 제거 지시가 원래 mock 유지 계획을 대체했다. `lib/tastemail/server.ts`의 `MailDataMode`와 `mailDataMode()`는 live만 제공한다. `GXWEBMAIL_DATA_MODE`로 mock을 활성화할 수 없으며 서버 장애 시 시연 데이터로 대체하지 않는다.
- API 주소는 서버 전용 `TASTEMAIL_API_URL`로 관리한다. 기본 loopback은 6711이며 원격 주소는 HTTPS만 허용한다. 개발 연결 폼도 현재 이 주소만 저장한다. 과거 7531·모드 전환법은 당시 기록이고 현재 실행 지침이 아니다.

- 프로필·공유 계정·기본 편지함 아이콘은 인증된 서버 설정을 SSR에서 읽고, 변경은 같은 출처 BFF를 통해 서버 응답이 확인된 후 반영하도록 연결했다. 서버 조회 실패를 정상 기본값으로 간주하거나 변경을 로컬 저장으로 성공 처리하지 않는다. 실제 배포 API 저장·조회 및 모바일 첫 화면은 아직 미검증이다.
- 위 아이콘 선택 창과 설정 초기화에는 상태별 복구 안내와 명시적인 서버 설정 재조회 버튼을 연결했다. 기존 컨트롤러는 GET만 수행하고, SSR 조회 실패 또는 계정 불일치 때는 인증된 서버 화면을 다시 요청한다. 충돌·미확정 변경은 자동 재전송하지 않는다. 10개 언어와 합성 핸들러·SSR·선택 창 회귀, 린트·빌드는 통과했지만 실제 장애·세션 만료·권한 거부 및 모바일 상호 작용 검증은 별개로 남아 있다.
- 같은 계정의 새 SSR 설정은 기존 provider를 유지한 채 layout effect에서 반영한다. 오래된 revision·다른 계정·저장 중 요청은 덮어쓰지 않고, 오류/미확정 잠금은 수동 재조회 전까지 유지한다. 개발·프로덕션 React SSR 및 제어된 effect 테스트는 통과했으나 실제 브라우저 페인트 시점과 모바일 깜빡임 제거를 입증하는 증거는 아니다.
- 개인 폴더/편지함 아이콘 및 트리 유형은 계정에 일치하는 서버 설정을 우선 사용하며, 아이콘 저장 시 displayKind를 보존한다. 새 항목 생성 후 서버 설정을 재조회하여 생성 유형을 저장한다. 유형 저장만 미확정이면 생성 요청을 반복하지 않고 유형 설정만 수동 재시도한다. 합성 테스트 범위의 연결이며 실제 서버 저장·배포·모바일 페인트 검증은 남아 있다. 서버 데이터 모델에서 서로 다른 mailbox 종류를 생성한다는 뜻은 아니다.
- 로컬 설정 이전은 설정 화면의 미리보기·배치 확인에 연결했다. 현재 계정·허용 대상만 읽고 기존 서버 설정을 보존하며 레거시 별칭을 설치된 ID로 변환한다. 최대 64개씩 명시적으로 확인하고 다음 배치는 새 설정에서 다시 준비한다. 브라우저 설정을 삭제하거나 자동 이전하지 않으며 실제 업로드는 미검증이다. 이전하지 않은 유형은 서버 기본값(편지함)으로 표시될 수 있으므로 기존 로컬 유형 보존에는 사용자 확인 이전이 필요하다.

GXWebMail의 합계 검사도 같은 의미이므로 파일별 제한으로 바꾸지 않았다. 작성 API에서 합계가 이 제한을 넘으면 JMAP 초안 생성 전에 `413 tooLarge`로 거부한다. 작성 창은 이 명시적 거부를 발송 결과 불명으로 잠그지 않으며, 업로드 파일 한 개와 메일당 첨부 합계 모두에 맞는 크기 제한 문구를 표시한다.

첨부 선택 준비 상태: live 작성 창에서는 발신 계정과 서버 첨부 한도가 로드되기 전, 업로드·제출 중, 제출 결과가 불명확한 동안 파일 선택 버튼과 드롭 영역을 비활성화한다. mock 작성 창의 첨부 시연은 유지한다. 변경 파일 ESLint와 프로덕션 빌드는 통과했다. 실제 브라우저에서 업로드 중 버튼 비활성화와 완료 후 재활성화를 확인했으며, 로드 전 선택 방지는 아직 검증하지 않았다.

임시보관 메일 재편집 메모: live 일반 텍스트 초안은 수신자·제목·본문·첨부·답장 참조 헤더를 작성 창에 다시 채운다. Rust JMAP은 초안 본문 변경을 `Email/set.update`로 지원하지 않아, 저장 시 새 초안을 만든 다음 이전 초안을 삭제한다. 서버는 삭제 전 개인 계정의 `$draft`와 Drafts 메일함 소속을 확인하며, 새 초안 저장 또는 발송이 확정되기 전에는 이전 초안을 삭제하지 않는다. 삭제 결과가 확인되지 않으면 성공 안내와 함께 이전 초안이 남을 수 있음을 표시한다. 기본 발신자와 다른 주소의 초안도 현재 `Identity/get`과 사용자 발신자 설정에 남아 있으면 원래 발신자를 유지하며, 삭제·비활성화된 발신자는 저장·발송하지 않는다. HTML 본문이 있는 초안은 서식 손실 경고를 확인한 뒤 일반 텍스트로 재편집할 수 있다. 별도 테스트 계정의 재편집·재저장·이전 초안 정리 1건은 확인했으며 발송 결과는 미검증이다.

답장·전달 연결 메모: live 메일 상세의 답장·전체 답장·전달 작성 창을 활성화했다. `Email/get`의 `replyTo`를 회신 주소로 우선 사용하고, 내가 보낸 메일은 다른 원래 수신자에게 답장한다. `messageId`·`references`는 답장 초안의 `inReplyTo`·`references`로 전달하고, 전체 답장 제출에서는 주 수신자를 유지하면서 추가 자기 주소(서버가 반환한 발신 별칭 포함)만 제외한다. 전달은 원본 본문을 인용하고 기존 첨부의 `m:{messageId}:{index}` blob을 새 초안에 참조한다. 20개를 넘는 첨부가 있는 메일은 전달 버튼을 비활성화한다. Rust JMAP 계약은 소스로 확인했으나 실제 계정의 초안·발송·첨부 보존 결과는 아직 검증하지 않았다.

격리 구현 메모: live 화면은 관리자 전용 `POST /api/admin/quarantine/{id}/release`(`target: inbox`)와 `POST /api/admin/quarantine/{id}/discard`를 같은 출처의 Next.js 경유로 연결했다. 해제·영구 삭제는 확인 대화상자를 거치고, 성공 응답의 ID·상태가 일치할 때만 완료로 표시한다. 응답 중단·5xx·파싱 실패는 처리 결과 불명으로 안내하고 자동 재요청하지 않는다. 일괄 처리는 미연동이고 실제 관리자 계정의 변경 결과는 검증하지 않았다.

첨부 파일 화면 구현 메모: live 모드는 더 이상 시연용 파일·용량·대용량 링크를 표시하지 않는다. JMAP `Email/query`의 `hasAttachment`, `attachmentName`, `from` 조건과 `Email/get`의 첨부 메타데이터를 사용해 실제 메일 첨부를 페이지 단위로 표시하고, 인증된 다운로드 프록시로 받는다. 페이지 수는 **첨부 개수가 아닌 메일 개수**를 기준으로 한다. 독립 파일 저장소·공유 링크·첨부만 삭제하는 정리 기능은 서버 계약이 없어 live 화면에 표시하지 않는다. 실제 계정의 보낸편지함에 있는 첨부 1개는 Next.js 경유 다운로드 응답과 메타데이터의 바이트 크기가 일치함을 확인했다. 같은 첨부 파일명의 검색 결과에서 원본 메일 ID와 첨부 blob ID가 일치함도 확인했다. 테스트 도메인의 실제 브라우저에서 첨부 목록이 표시되고 `pdf` 검색이 PDF 항목으로 좁혀지며 검색어를 지우면 원래 목록으로 돌아오는 것을 확인했다. 파일 화면의 실제 첨부 링크가 같은 출처의 인증 프록시를 가리키고 클릭 뒤에도 파일 목록에 남는 것을 확인했다. 별도 테스트 계정의 `/files` 화면에서 무해한 테스트 첨부를 브라우저로 내려받았고, 저장된 117바이트 파일의 SHA-256이 업로드 원본과 일치했다. 다른 검색 조건은 미검증이다.

캘린더 구현 메모: 새 일정에는 참석자 이메일을 최대 100개까지 입력할 수 있으며 서버의 `attendeeUsernames` 계약으로 전달한다. 서버는 초대장을 발송할 수 있으므로 화면에 외부 효과를 미리 알린다. 참석자가 있는 일정의 취소는 현재 revision을 확인한 뒤 서버에 전달하며 서버가 취소 알림을 처리한다. 참석자가 있는 일정을 수정할 때 서버 계층이 현재 revision과 참석자 목록을 다시 읽어 `attendeeUsernames`에 그대로 전달하므로 기존 목록을 빈 목록으로 덮어쓰지 않는다. 화면은 변경 초대장 발송과 참석 응답 초기화 가능성을 저장 전에 확인받으며 참석자 목록 자체의 편집은 제공하지 않는다. Rust 저장소는 수정 시 참석자 행을 재생성하므로 기존 로컬 참석 응답이 기본값으로 돌아갈 수 있다. 참석자 목록 보존을 포함한 합성 API 검증은 통과했지만 실제 계정의 초대 발송·초대 일정 수정·취소는 검증하지 않았다.

캘린더 참석자 변경 확인: 수정 화면의 브라우저 기본 `confirm` 대신 앱 내부 확인 대화상자를 사용한다. 사용자가 저장을 확정하기 전에는 변경 요청을 보내지 않으며, 취소하면 편집 내용을 유지한다. 변경 파일 ESLint·TypeScript 검사는 통과했다. 실제 참석자가 있는 테스트 일정의 변경·초대장 발송은 수행하지 않았다.

캘린더 그리드 후속 변경: live 일정이 자정을 넘거나 여러 날 이어질 때 월 보기의 각 날짜와 일·주 보기의 해당 시간대에 나누어 표시한다. 종일 일정은 일·주 보기의 별도 행에 표시하며 종료 날짜는 제외한다. 날짜 경계와 DST 당일의 벽시계 시간 배치를 대상으로 투영 함수를 확인했고, 10개 언어 키 검사·변경 파일 ESLint·TypeScript·프로덕션 빌드가 통과했다. 실제 서버의 종일·장기 일정 데이터가 있는 계정에서의 화면 배치와 모바일 날짜 선택은 아직 검증하지 않았다.

모바일 live 캘린더에는 현재 주의 날짜 7개를 선택하는 줄을 추가했다. 날짜를 누르면 해당 날짜의 일 보기로 전환하고, 일정이 있는 날짜에는 표시점을 둔다. 로컬 개발 서버에서 데스크톱 캘린더의 로드는 확인했지만, 모바일 너비에서의 터치 선택·줄바꿈과 실제 일정의 상세 표시·콘솔 오류까지 확인한 것은 아니다.

접근성 보고서 경계: 별도 `/accessibility` 페이지의 KWCAG 통과 판정·명암비·고정 자체 점검 날짜는 `lib/mock-accessibility.ts`의 시연 데이터다. live 모드에서는 이를 실제 감사 결과처럼 표시하지 않고 10개 언어의 명시적 안내만 보여 준다. 인증된 테스트 도메인의 `/ko/accessibility`에서 안내가 렌더링되고 시연 통과 목록은 표시되지 않음을 확인했다. mock 모드의 시연 보고서는 유지한다. 이는 실제 접근성 감사·인증을 수행했다는 뜻이 아니다.

단축키 경계: `/shortcuts`의 참조 목록과 `/settings/shortcuts`의 편집 폼은 실제 전역 키 입력 처리와 연결되지 않은 템플릿 시연이다. live 모드에서는 동작하는 설정처럼 보이지 않게 두 화면을 명시적 미구현 안내로 바꾸고, mock 모드의 시연 화면은 유지한다. 인증된 테스트 도메인의 두 한국어 경로에서 안내를 확인했고 관찰한 콘솔 오류는 없었다. 실제 키보드 단축키 기능은 아직 구현하지 않았다.

세션 구현 메모: 브라우저가 HTTPS로 접속한 요청은 Next.js가 개발 모드여도 HttpOnly 세션 쿠키에 `Secure`를 설정한다. live 로그인 화면은 HTTPS 또는 로컬 loopback HTTP에서만 제출하고, 세션 POST 경로는 같은 출처 `Origin`을 요구하며 요청 본문을 읽기 전에 원격 평문 HTTP를 거부한다. 프록시의 `Host`/`X-Forwarded-Proto` 전달과 HTTPS 종단 설정은 배포 측에서 확인해야 하며, 이 검사만으로 이미 전송된 평문 자격 증명을 보호할 수 없다. 세션 확인 중 Rust API가 401을 반환하면 로컬 세션 쿠키를 삭제하고, 401·403·429·일시적 서버 오류를 구분해 전달한다. HTTP 200의 JMAP 세션 본문이 잘못된 JSON이거나 `apiUrl`·기본 메일 계정·해당 계정 객체가 빠졌다면 네트워크 장애가 아닌 응답 형식 오류(502 `unavailable`)로 표시하고 보호된 업무·관리자 셸을 열지 않는다. 업무 화면이 보이는 동안 60초 간격으로, 탭이 다시 활성화됐을 때에도 마지막 확인 후 60초 이상 지났다면 세션을 재확인하고, 401이면 로그인 화면으로 이동한다. 잘못된 JSON과 필수 필드 누락 사례를 포함한 합성 API 검증은 통과했지만 실제 계정 세션 만료는 검증하지 않았다.

로그인 페이지 구현 메모: live `/[locale]/login`은 서버 페이지에서 세션 쿠키가 있을 때만 JMAP 세션을 확인해 유효한 세션을 해당 locale 홈으로 이동한다. 쿠키가 없는 익명 방문자는 불필요한 `/api/mail/session` 401 요청 없이 클라이언트 로그인 폼을 받는다. `username`만 있고 기본 메일 계정 정보가 빠진 불완전한 세션은 홈으로 리다이렉트하지 않고 로그인 폼을 유지한다. 입력 필드에는 명시적인 `id`와 `name`을 지정했다. live 모드의 2단계 인증 안내는 Rust가 실제 `mfaRequired`를 반환한 경우에만 표시하며, 인증 필요 여부를 모르는 익명 화면에서 계정에 MFA가 활성화됐다고 단정하지 않는다. 테스트 도메인의 익명 로그인 화면에서 401·폼 필드 콘솔 경고가 사라진 것을 확인했으며, 합성 API 검증에서 익명·불완전한 세션의 폼 렌더링과 인증된 로그인 페이지의 307 이동을 확인했다.

MFA 검증 경계: Rust `POST /api/auth/session`은 코드가 필요하면 HTTP 401 `mfaRequired`, 코드가 틀리거나 이미 사용됐으면 HTTP 401 `invalidMfaCode`를 반환한다. Next.js 세션 경로와 기존 합성 계약 검증은 두 상태 및 올바른 코드의 로그인 성공을 포함한다. GXWebMail의 MFA 입력칸은 영문 복구 코드도 입력할 수 있도록 모바일 숫자 키패드 강제를 제거했고 기존 Web Mail과 같이 32자로 제한한다. 이는 실제 MFA 설정 계정의 코드 입력·복구 코드 사용·브라우저 로그인 성공 검증을 대체하지 않는다.

페이지 접근 경계: live 모드의 업무·설정 경로는 URL을 바꾸지 않는 `(workspace)` 서버 레이아웃에서 JMAP 세션을 확인한다. live 관리자 경로도 같은 확인을 거친다. 쿠키가 없거나 Rust가 401을 반환하면 로그인으로 이동한다. 403 권한 부족과 429 요청 제한은 각각 해당 상태 화면으로 표시하고, 일시적인 서버 장애는 로그인 만료로 간주하지 않고 재시도 화면을 표시한다. 클라이언트 전환에도 공통 업무 셸이 세션을 다시 확인하며, 이 브라우저 요청이 20초를 넘기면 재시도 화면으로 전환한다. 합성 루프백의 업무·관리자 경로에서 401의 로그인 이동과 403·429·503의 상태 화면을 확인했다. 로그인·가입·설치 경로는 공개하고, mock 데모 모드의 기존 접근 방식은 유지한다. 개별 API의 인증·권한 검사는 이 페이지 경계와 별도로 유지한다. 실제 배포 계정의 만료·복구 시나리오는 아직 검증하지 않았다.

로그아웃 구현 메모: Rust `DELETE /api/auth/session`의 204(또는 이미 유효하지 않은 401)에서만 서버 세션 폐기를 확인된 것으로 표시한다. 그 밖의 응답·연결 오류에서는 로컬 HttpOnly 쿠키를 삭제하되 `signout_unconfirmed`로 구분하고, 사용자에게 서버 세션 폐기 미확인을 알린다. Next.js 경로 자체에 요청이 닿지 않으면 로그인 화면으로 이동하지 않고 재시도를 안내한다. 실제 계정으로 별도 검증 세션을 생성해 Next.js 경유 로그인·세션 확인·로그아웃·로그아웃 후 세션 확인을 순서대로 호출했으며 HTTP 200·200·200·401을 확인했다. 서버 폐기가 503으로 확인되지 않은 합성 사례에서는 `signout_unconfirmed` 503과 로컬 쿠키 삭제를 확인했고, 쿠키가 없는 반복 로그아웃은 `signed_out`으로 확인했다. 브라우저의 기존 세션은 로그아웃하지 않았다.

보안 화면 구현 메모: live `/security`와 `/settings/security`는 Rust의 `GET /api/user/security`에서 TOTP 상태·남은 복구 코드 수·로그인 세션·보안 이벤트를 읽어 표시한다. API 변환 계층은 이벤트의 임의 `detail` 필드를 브라우저로 전달하지 않는다. 확인 대화상자 뒤에 `DELETE /api/user/security/sessions/{session_id}` 또는 `DELETE /api/user/security/sessions`로 다른 기기 세션을 해제하며, 현재 세션은 Rust가 거부하고 UI에서도 대상으로 내놓지 않는다. 성공 응답 후에만 완료를 알리고 실패·응답 불명확 시 목록을 다시 읽는다. mock 보안 점수·가짜 기기/이벤트·가짜 MFA 재발급 동작은 live에서 표시하지 않는다. 그 밖의 실제 보안 설정 변경은 미연동이다. 실제 테스트 계정의 `/ko/security`에서 2단계 인증 상태·로그인 기기 및 세션·최근 보안 활동 섹션이 렌더링되는 것을 확인했다. 세션 해제 결과는 검증하지 않았다.

서명 설정 구현 메모: live `/settings/signature`는 Rust `GET/PATCH /api/user/preferences`의 `identities`와 발신자별 `mailSignature`·`mailSignatureHtml`·`mailSignatureFormat`을 사용한다. mock의 다중 서명 목록과 자동 적용 스위치를 서버 기능으로 오인하지 않도록 별도 화면으로 분리했다. 브라우저 조회에는 25초, 저장에는 30초 제한 시간을 두고, 저장 결과가 불확실하면 서버 값을 다시 읽는다. live 작성 창은 일반 텍스트와 서식 HTML 본문을 모두 지원한다. 2026-09-30 후속 변경으로 새 개인 메일의 작성 옵션에서 선택된 발신자의 텍스트·HTML 서명과 형식을 함께 읽고, 본문이 비어 있으며 사용자가 아직 입력하거나 편집 모드를 바꾸지 않았을 때만 적용한다. HTML 서명은 편집기의 허용 태그·링크로 한 번 더 제한하며 텍스트 대체 본문도 함께 유지한다. 초안 재편집·기존 본문에는 자동 추가하지 않고, 공용 편지함은 서버의 기존 텍스트 서명만 사용한다. 서로 다른 서명의 기본·보조 발신자를 둔 합성 JMAP 작성 옵션 계약에서 각 발신자 선택 결과와 계정에 없는 발신자에 대한 403 거부를 확인했으며, 실제 계정의 서명 저장·작성 화면·발송 연계는 검증하지 않았다.

계정 설정 구현 메모: live `/settings/account`는 같은 사용자 환경설정 API의 실제 `identities`에서 발신 주소·표시 이름·기본 발신자를 읽기 전용으로 보여 준다. mock 화면의 표시 이름·회신 주소·별칭 편집은 TASTEMAIL 사용자 계정 변경 API로 확인되지 않았으므로 live 화면에 표시하지 않는다. 합성 루프백에서는 live 경로 접근과 API 발신자 응답, mock 경로의 기존 편집 화면 분리를 확인했다. 테스트 도메인의 인증된 브라우저에서 계정 설정 화면에 발신 주소 1개가 기본 발신 주소로 읽기 전용 표시되는 것을 확인했다. 이 화면 관찰만으로 API 원문과의 필드별 일치나 다른 별칭이 있는 계정의 표시까지 검증한 것은 아니다.

임시저장 오류 경계: `Email/set` 초안 생성 요청 뒤 응답이 끊기거나 생성 결과가 불명확하면 `draft_uncertain`으로 표시한다. 브라우저의 임시저장 요청도 30초 제한 시간을 두고, 네트워크·응답 파싱 실패는 생성 여부 불명으로 처리한다. 작성 창은 같은 내용을 다시 저장하거나 발송하지 않도록 잠그고 임시보관함 확인을 안내한다. 명시적인 `notCreated` 응답은 생성 실패로 구분한다. 실제 계정의 정상 초안 저장은 확인했지만 응답 중단 사례는 미검증이다.

작성·첨부 업로드 경계: Next.js의 작성 POST와 업로드 POST는 같은 출처 `Origin`이 없는 요청을 거부한다. 브라우저 업로드에는 120초 제한 시간을 적용하고, Next.js에서 Rust 업로드 요청에는 별도로 60초 제한 시간을 둔다. 업로드 시간 초과는 메일 발송 성공으로 표시하지 않는다. 별도 테스트 계정의 정상 첨부 업로드·초안 저장·다운로드 일치와 첨부 없는 자기 수신 발송 1건을 확인했다. 업로드 시간 초과와 첨부 발송은 검증하지 않았다.

받는 사람 자동완성 경계: live 작성 창은 인증된 Next.js 경로를 통해 Rust `GET /api/contacts/suggestions`에 검색어와 최대 8건 제한을 전달한다. 추천 응답은 계정 범위의 저장 연락처와 사용 이력을 포함하며, 선택 시 이메일 주소만 수신자로 추가한다. mock 작성 창은 API를 호출하지 않는다. 합성 루프백에서 검색어·8건 제한 전달과 추천 항목의 필드 변환을 확인했다. 테스트 도메인의 인증된 실제 계정 작성창에서 일반 검색어 입력 후 추천 1건이 표시되고 Enter 키로 수신자 칩에 추가되는 것을 확인했다. 테스트 입력은 저장하지 않고 폐기했으며 메일은 발송하지 않았다. 터치 선택과 여러 추천 항목의 탐색은 아직 검증하지 않았다.

외부 수신자 경고 경계: live 작성 창은 선택된 발신 주소의 도메인을 기준으로 To/Cc/Bcc와 아직 확정하지 않은 To 입력을 비교한다. mock 작성 창은 기존 시연 도메인을 유지한다. 테스트 도메인의 별도 브라우저 탭에서 합성 외부 주소 입력 시 경고가 나타나고 발신자와 같은 도메인 주소로 바꾸면 사라지는 것을 확인했다. 이 확인에서는 발송·임시저장·첨부 업로드를 하지 않았다.

기준: 2026-09-28의 `tastedev-mail` 소스(`crates/tastemail-api/src`, `apps/webmail/src`)와 GXWebMail의 현재 mock 화면. 아래의 **소스 지원**은 Rust 소스에 경로·메서드가 있다는 뜻이다. 실제 계정으로 확인한 항목과 아직 검증하지 않은 항목은 각 구현·검증 메모에서 별도로 구분한다.

## 연결 확인 상태

- Rust 소스에는 무인증 `GET /health`, 인증 `POST/DELETE /api/auth/session`, 인증 JMAP `GET /.well-known/jmap`와 `POST /jmap/api`가 있다.
- 배포 주소 `http://192.168.0.109:7531`에서 무인증 `GET /health`는 HTTP 200과 `{"status":"ok","service":"tastedev-mail"}`를 반환했고, 무인증 `GET /.well-known/jmap`는 HTTP 401을 반환했다. 이는 네트워크 연결과 인증 경계만 확인하며 실제 계정 로그인이나 배포 소스 버전 일치는 증명하지 않는다.
- 같은 포트의 `https://192.168.0.109:7531/health`는 TLS 프레임 오류로 연결되지 않았다. 설치 화면은 API URL을 설정할 수 있지만 사설망 평문 HTTP를 인증용 설정으로 저장하지 않는다. 다른 장비의 API에는 HTTPS 또는 Next.js 호스트의 로컬 터널이 필요하다.
- 소스의 `config/tastedev-mail.toml`과 Linux Web Mail 서비스는 `http://127.0.0.1:7531`을 사용한다. GXWebMail live 모드의 서버 전용 API 기본 주소도 동일하며, **Next.js 프로세스가 실행되는 호스트**의 loopback을 가리킨다.
- Windows 개발 장비에서 `192.168.0.109:22` TCP 연결과 기존 SSH 설정의 비대화형 인증을 확인했다. `ssh -N -L 127.0.0.1:7531:127.0.0.1:7531 <SSH_USER>@192.168.0.109` 방식의 로컬 터널을 열어 `127.0.0.1:7531/health`와 Next.js `/api/mail/health`가 모두 200인 것을 확인했다. 무인증 JMAP과 세션 경로는 예상대로 401이다. 터널은 현재 개발 세션의 일시적 프로세스이며 서버 설정은 변경하지 않았다.
- 터널을 통한 Next.js 세션 POST에 임의의 존재하지 않는 `invalid.test` 사용자로 한 번만 인증 실패를 확인했다: HTTP 401 `unauthorized`. 실제 계정이나 메일 데이터는 사용하지 않았다. 비로그인 업무 경로 `/ko`, `/ko/calendar`, `/ja/settings`, `/en/mailboxes`는 각각 언어별 로그인으로 307 이동하고, `/ko/login`과 `/ko/setup`은 200으로 열렸다. 이는 MFA나 실제 계정 세션 성공을 증명하지 않는다.
- `/calendar`에 대한 비로그인 접근을 `ko`, `en`, `de`, `es`, `fr`, `it`, `pt`, `ja`, `zh`, `zh-hant` 10개 언어에서 확인했다. 모두 307로 자신의 언어별 `/login`으로 이동했다. 이 확인은 렌더링·모바일 레이아웃·실제 로그인 검증을 대체하지 않는다.
- live 로그인은 `/health` 응답을 선행 조건으로 삼지 않고, 같은 출처의 `/api/mail/session`으로 인증을 시도한 결과를 표시한다. 무인증 `/api/mail/health`는 선택적 진단 경로이며 실제 계정 인증 성공의 증거가 아니다.
- Rust API 라우터에 `GET /api/auth/session`은 없다. 현재 세션 검사는 토큰을 사용한 JMAP 세션 조회 등 실제로 제공되는 인증 경로를 사용해야 한다.
- 브라우저와 Next.js 사이의 로그인 제출은 HTTPS 또는 브라우저의 로컬 loopback HTTP에서만 허용한다. Next.js와 Rust API 사이의 인증 요청도 HTTPS 또는 서버 내부 loopback으로 제한한다. 무인증 LAN `/health` 확인은 로그인 전송 경로의 안전성을 증명하지 않는다.
- 개발 도메인 `https://webmail-test.gxsoft.co.kr`은 2026-09-28 초기 확인에서 무인증 `GET /`, `/ko`, `/ko/login`이 HTTP 500을 반환했다. 이는 당시 관측이며 현재 상태는 아래의 실제 로그인 확인으로 대체한다. 저장소의 `deploy/nginx/webmail-test.gxsoft.co.kr.conf`가 실제 서버에 적용되었는지는 별도로 확인하지 않았다.
- 2026-09-29에는 `http://127.0.0.1:7540/ko/login`과 `https://webmail-test.gxsoft.co.kr/ko/login`의 개발 서버에서 로그인 화면은 렌더링되지만 React hydration이 완료되지 않아 제출이 GET으로 바뀌는 문제를 확인했다. 개발 WebSocket 요청의 Origin 차단을 확인하고 `next.config.ts`의 `allowedDevOrigins`에 `127.0.0.1`과 테스트 도메인을 추가했다. 두 출처에서 실제 계정으로 로그인하여 `/ko`의 받은편지함 목록을 확인했고, 테스트 도메인에서 받은편지함 86통과 `TASTEMAIL` 검색 결과 18건을 확인했다. 보낸편지함의 기존 메일 1건에서 상세 화면, 격리된 HTML 본문, 첨부 3개의 메타데이터가 표시되는 것을 확인했으며 받은편지함의 1–50/86 → 51–86/86 → 1–50/86 페이지 이동도 확인했다. 첨부 다운로드·상태 변경·발송·MFA·세션 만료 검증을 대체하지 않는다.

## 미지원 또는 별도 계약이 확인되지 않은 GXWebMail 기능

이 표의 항목은 **현재 확인한 Rust API 라우터와 기존 TASTEMAIL Web Mail 사용 경로에 직접 대응하는 계약이 없음**을 뜻한다. 서버 전체에서 영구적으로 불가능하다는 단정은 아니며, 서버 버전이나 API 계약이 바뀌면 다시 확인한다. live 모드에서는 연결 기능인 것처럼 mock 결과를 조용히 보여주지 않는다.

| 화면·기능 | 현재 판단 | 처리 방향 |
| --- | --- | --- |
| 수신 HTML 메일의 원본 디자인 재현 | 2026-09-29에 확인한 배포 화면에서는 뉴스레터의 숨김 프리헤더가 빈 공간으로 나타나고 다크 디자인이 흰 배경으로 표시됐다. 당시 서버 정화 규칙은 `<style>`과 인라인 스타일을 제거했다. 로컬 `tastedev-mail` 소스의 `sanitize_received_html`은 제한된 CSS 속성과 안전한 HTTPS 배경 이미지를 보존하고, CSS 배경도 `blockedExternalImages` 판정에 포함하도록 변경됐다. 관련 Rust Debug·Release 테스트는 통과했다. 2026-09-30 원격 설치 패키지와 `/usr/bin/tastemail --version`은 모두 `0.1.2`를 반환했고, 바이너리 SHA-256은 설치 전 값과 달랐다. `tastemail.service`는 02:51 KST부터 active이며 `/health`가 200을 반환했다. 이후 사용자가 제공한 Witcher 메일의 데스크톱 캡처에는 배경 이미지가 표시된다. 다만 캡처만으로 서버 실행 바이너리의 정확한 소스 버전, 원본 MIME의 배경 표현, 모바일 배치의 완전한 재현은 증명하지 못한다. | 메일 목록의 본문 전송량과 이미지 많은 메일의 표시 지연 | 개인·공용 메일 목록은 최대 50건의 목록용 속성만 요청하고, 본문이 없는 응답이면 선택한 한 통만 상세 조회한다. 기존 전체 본문 응답은 즉시 표시한다. 상세 로딩·오류·재시도 중 목록을 유지한다. 합성 JMAP 검사에는 두 응답 형태를 추가했지만 개발 서버와 빌드 산출물을 공유하므로 전체 검사는 아직 재실행하지 않았다. 현재 로컬 Rust `email_get`은 `properties`와 본문 조회 플래그를 무시하고 MIME에서 본문·헤더·첨부를 추출하므로 서버 변경·배포 전에는 전송량과 추출 작업이 줄지 않는다. 외부 이미지는 별도 HTTPS 호스트에서 브라우저가 가져오므로 Sims 뉴스레터의 단계적 표시를 API 지연으로 단정할 수 없다. GXWebMail은 iframe 중복 생성을 피하고 목록 응답에 `Server-Timing`을 제공한다. 실제 시간은 인증된 브라우저 세션에서 미측정이다. | `tastedev-mail` 작업에 선택 속성 계약 구현을 요청했다. 서버 계약·배포 버전을 확인한 뒤 개인·공용 목록/상세 결과와 브라우저 네트워크 시간을 검증한다. |

## 다음 확인 게이트

발송 경로는 개인 계정의 기본 발신 ID와 첨부 제한을 JMAP 세션·사용자 환경설정에서 확인한다. 초안 생성 후 제출 응답이 끊기거나 불명확하면 중복 제출을 피하도록 작성 창의 보내기 동작을 잠그고, 보낸편지함·임시보관함을 확인하도록 안내한다. 이 보호의 장애 동작은 실제 서버에서 검증하지 않았다. 무해한 테스트 첨부의 업로드·초안 저장·다운로드와 첨부 없는 자기 수신 발송 1건은 별도 테스트 계정에서 확인했다. 추가 발송은 새 범위가 승인되기 전까지 수행하지 않는다.

별도 테스트 계정의 브라우저 세션을 확인했고, 변경 검증 전 기준 상태로 받은편지함 6통과 임시보관함 0통을 읽었다. 이 조회는 초안 저장이나 발송 성공을 증명하지 않는다.

같은 테스트 계정에서 수신자 없는 일반 텍스트 메일을 임시 저장했다. 성공 안내 뒤 임시보관함에 1통이 나타났고, 새로고침 후 다시 진입해도 제목과 본문이 유지됐다. 서버가 이 초안을 HTML 본문으로도 투영해 기존 UI의 ‘HTML이면 편집 버튼 숨김’ 조건에 걸리는 문제를 확인했다. HTML 본문이 있는 초안도 서식 소실 안내를 확인한 뒤 텍스트 편집기로 열 수 있게 수정했다. 본문을 변경해 재저장한 결과 수정 내용이 표시됐고 임시보관함은 1통으로 유지돼 이 사례에서 기존 초안 정리가 확인됐다. 테스트 초안 1통은 남겨 두었다. 이 사례만으로 발송이나 응답 중단 시 초안 중복 방지가 검증된 것은 아니다.

같은 별도 테스트 계정의 받은편지함에서 기존 중요 표시가 꺼진 메일 1건을 선택해 표시를 켰고, 서버 응답 후 켜짐을 확인했다. 이어 같은 메일의 표시를 다시 끄고 새로고침 후에도 꺼진 상태임을 확인했다. 이는 중요 표시 변경·원상복구 1건의 실제 브라우저 검증이며, 읽음·이동·삭제나 실패 응답 시 복구의 검증은 아니다.

메일 읽기 창에 읽음·미읽음 전환 버튼을 추가했다. 기존 서버 `seen` 플래그 변경 경로를 사용하며 mock 모드에서도 같은 조작을 제공한다. 별도 테스트 계정의 기존 읽음 메일 1건을 미읽음으로 바꾼 뒤 화면의 버튼이 읽음 동작으로 전환되는 것을 확인했고, 다시 읽음으로 복구했다. 새 검색 조회에서 해당 메일의 `is:unread` 결과가 원래대로 0건임을 확인했다. 변경된 입력에 대해 `npm run check:locales`, 두 변경 컴포넌트의 ESLint, `npx tsc --noEmit`, `npm run build`가 통과했다. 다른 계정·메일함과 실패 응답 시 복구는 아직 검증하지 않았다.

같은 테스트 계정의 기존 받은편지함 메일 1건을 보관함으로 이동했다. 받은편지함은 6통에서 5통으로 줄고 대상 메일이 목록에서 사라졌으며 보관함 1통에 나타났다. 보관함에서 받은편지함으로 되돌린 뒤 새로고침해도 받은편지함 6통과 대상 메일이 다시 표시됐다. 이는 보관·복구 왕복 1건의 실제 브라우저 확인이다.

같은 테스트 메일을 받은편지함에서 스팸으로 옮겼다. 받은편지함은 6통에서 5통으로 줄고, 기존 1통이던 스팸함은 대상 메일을 포함해 2통이 됐다. 스팸함에서 받은편지함으로 복구한 뒤 스팸함은 1통, 받은편지함은 6통으로 돌아왔고 새로고침 후에도 대상 메일이 받은편지함에 표시됐다. 이는 스팸 이동·복구 왕복 1건의 실제 브라우저 확인이며, 휴지통·사용자 지정 편지함 이동과 오류 시 복구는 아직 검증하지 않았다. 브라우저 자동화의 포인터 클릭은 화면에서 반응하지 않았지만 키보드 활성화는 정상 동작했으므로 이를 앱 hydration 오류로 판정하지 않았다.

같은 테스트 계정의 HTTPS 브라우저 세션에서 `has:attachment` 검색 페이지를 새로고침한 뒤에도 로그인 상태와 결과 3건이 유지됐다. 이어 `ko`, `en`, `de`, `es`, `fr`, `it`, `pt`, `ja`, `zh`, `zh-hant`의 설정 경로에 직접 진입해 각 언어 경로와 인증된 업무 셸·설정 제목이 렌더링되는 것을 확인했다. 이탈리아어·포르투갈어는 첫 관찰이 로딩 중이어서 렌더링 완료 후 다시 확인했다. 이는 언어별 인증 화면의 브라우저 렌더링 확인이며, 10개 언어의 모든 상호작용·번역 정확성·콘솔 오류 검증이나 실제 세션 만료 검증은 아니다.

영어 설정 화면에서는 `Open menu` 버튼을 실제로 눌러 확장 상태와 업무 탐색 항목이 나타나는 클라이언트 동작을 확인했다. 이 한 화면의 상호작용은 나머지 언어와 화면의 hydration 검증을 대체하지 않는다.

## 현재 구현 상태

- 개인 메일: 서버 전용 인증·JMAP 변환 계층, 개인 편지함·목록·본문·검색·첨부 다운로드를 연결했다. 역할 없는 사용자 지정 편지함은 목록과 검색 필터에서 현재 계정의 ID를 대조해 조회한다. 읽음·별표 및 시스템 편지함 간 이동은 서버 응답 후 목록을 다시 읽는다. 시스템 편지함의 메일을 사용자 지정 편지함으로 이동하는 경로도 계정의 실제 편지함 ID를 검사한 뒤 연결했다. 사용자 지정 편지함 생성·이름 변경·삭제는 현재 Rust HTTP/JMAP 계약이 없다.
- 작성: 일반 텍스트 작성, 명시적 임시저장, 초안 재편집, 첨부 업로드, 발송 큐 제출을 소스 계약에 맞춰 연결했다. 제출 결과가 불명확할 때 자동 재시도하지 않는다. 휴지통 메일의 영구 삭제는 소스 계약에 맞춰 연결했지만 실제 계정으로는 검증하지 않았다. live 작성창의 서식 모드는 일반 텍스트 대체 본문과 선택적 HTML 본문을 함께 API에 보내고 JMAP `textBody`·`htmlBody`로 변환한다. live 편집기에 새로 삽입한 이미지는 인라인 데이터 URL 대신 첨부로 처리한다. 개인·공용 HTML 초안의 안전한 서식과 일치하는 CID 이미지 참조·inline 첨부 메타데이터를 재사용하며 외부 이미지 등 복원 불가 리소스는 서식 손실 확인 후 텍스트 편집으로 제한한다. 실제 재저장 및 HTML 발송 결과는 아직 미검증이다. 예약 발송은 서버가 광고한 `maxDelayedSend` 한도 안에서 `HOLDUNTIL`로 개인·공용 제출 경로에 연결했고 합성 계약에서 정상·범위 초과·권한 거부를 확인했다. 실제 계정의 예약·전달·취소는 미검증이다.
- 다른 업무: 개인 주소록 조회·추가·편집·삭제, 월별 일정 조회와 본인 일정 변경·참석 응답·참석자 초대 생성, 결재 요청·승인·반려, 메일 규칙 조회·편집·문법 검사·미리보기, 관리자 권한의 격리 조회·해제·삭제를 연결했다. AI 제안·조직도·회의실 현황 등 서버 계약 없는 시연 기능은 live 결과로 표시하지 않는다.
- 공용 편지함: 서버 목록과 JMAP 세션의 공유 계정 읽기 권한을 확인해 편지함·메일·첨부를 읽는다. `mayWrite` 공용 계정의 읽음·미읽음·별표 변경, 같은 계정의 허용된 편지함 간 이동·휴지통 내 영구 삭제와 `mayRead`·`mayWrite`·`maySend` 공용 계정의 새 초안·기존 초안 재편집·발송을 합성 계약에서 확인했다. 2026-10-01 공유 테스트 계정에서 초안 저장·재편집·교체 시 중복 없음, 동일 공유 주소 자기 발송·수신과 본문 일치, 별표 변경·복원 및 새로고침 유지를 확인했다. 공유 보관함·스팸·휴지통 이동·받은편지함 복원 및 새로고침 후 동일 본문 유지도 확인했다. 120바이트 공유 첨부 자기 발송·수신과 다운로드 SHA-256 일치도 확인했다. 공유 영구 삭제·대용량 첨부·예약·권한 거부 조합은 미검증이고, 권한 편집은 미연동이다. HTML 본문은 Rust가 정화한 값을 sandbox iframe에 격리한다. 새 사용자 설정은 HTTPS 외부 이미지를 표시하고, 기존 저장 설정의 차단 정책과 메일별 선택은 유지한다.
- 검증 범위: 실제 계정의 로컬·테스트 도메인 로그인, 받은편지함 목록·페이지 이동, 테스트 도메인의 기본 검색 결과, 보낸 메일 1건의 상세·HTML 본문·첨부 메타데이터를 확인했다. 로컬 Next.js 경유로 보낸편지함의 첨부 1개(51,712바이트)를 내려받아 HTTP 200, `application/octet-stream`, 응답 바이트 수와 메타데이터 크기 일치를 확인했다. 테스트 계정의 별표·읽음 전환과 받은편지함↔보관함·받은편지함↔스팸 이동은 각각 원상복구까지 확인했다. 별도 테스트 계정에서 일반 텍스트 초안 저장·재편집·재저장과 첨부가 있는 별도 초안의 저장·새로고침 후 재진입·다운로드 SHA-256 일치를 확인했다. 같은 계정에서 117바이트 텍스트 첨부가 있는 자기 수신 메일 1통의 발송·수신과 첨부 바이트·SHA-256 일치도 확인했다. 파일 화면의 테스트 첨부 브라우저 다운로드도 크기·SHA-256이 일치했다. 외부 도메인 전달·SMTP 최종 전달 보장·발송 실패, MFA·세션 만료, 모바일·데스크톱 전체 회귀는 아직 검증하지 않았다. 2026-09-29 변경된 프로덕션 빌드와 `npm run test:mail-adapter`의 합성 API 사례는 통과했다. mock 모드는 독립적으로 유지한다.
- 2026-09-29 재확인: 기존 SSH 로컬 터널이 없는 동안 로컬 `127.0.0.1:7540/api/mail/health`와 테스트 도메인의 `/api/mail/health`는 모두 HTTP 503 `retryable`이었고, 로그인 화면은 메일 서버 연결 실패를 표시했다. 제한 없는 무인증 조회에서 `192.168.0.109:7531/health`는 HTTP 200과 TASTEMAIL 식별 응답을 반환해 Rust API 자체의 장애는 아니었다. 기존 SSH 설정으로 `127.0.0.1:7531` 로컬 터널을 다시 열자 로컬 API와 두 Next.js 출처의 상태 경로가 모두 HTTP 200으로 회복됐다. 별도 테스트 세션의 로컬 로그인·세션 확인·받은편지함 첫 페이지는 각각 HTTP 200(50건/전체 87건)이었고, HTTPS 테스트 도메인의 로그인·세션 확인도 HTTP 200이었다. 두 테스트 세션은 각각 로그아웃 HTTP 200으로 정리했으며 브라우저의 기존 세션은 유지했다. live 연결은 현재 Next.js 호스트의 SSH 터널 지속 여부에 의존하므로, 임시 터널 종료 후에는 같은 실패가 재발할 수 있다.
- 같은 날 별도 임시 세션에서 `is:unread`의 Next.js 검색 결과와 Rust JMAP `Email/query`의 `notKeyword: "$seen"` 직접 조회를 비교했다. 전체 64건과 첫 페이지 50건이 같고, 첫 페이지의 ID 순서도 일치했다. 이 세션 역시 HTTP 200 로그아웃으로 종료했다. 이는 미읽음 검색의 읽기 경로 검증이며 다른 검색 문법이나 메일 상태 변경의 검증은 아니다.
- 별도 임시 세션에서 Rust JMAP `Mailbox/get`과 Next.js `/api/mail/mailboxes`를 비교했다. 실제 6개 메일함의 ID·역할·전체·미읽음 수가 모두 일치했고, 받은편지함·임시보관함·보낸편지함·보관함·스팸·휴지통의 첫 페이지 `total`도 각각 해당 서버 메일함의 `totalEmails`와 일치했다. 임시 세션은 HTTP 200 로그아웃으로 종료했다. 이 검증은 목록 내용이나 상태 변경의 일치를 의미하지 않는다.
- 실제 계정의 별도 임시 세션에서 TASTEMAIL 직접 GET과 Next.js 경유 GET을 비교했다. 연락처 1건의 ID·표시 이름·주소·수정 시각, 2026년 9월 일정 1건의 ID·revision·상태·응답·시작/종료 시각이 일치했다. 결재는 양쪽 모두 0건이어서 빈 목록 경로만 확인됐다. 임시 세션은 HTTP 200 로그아웃으로 종료했다. 화면 렌더링이나 변경 기능의 검증을 대체하지 않는다.
- 공용 편지함과 메일 규칙도 별도 임시 세션의 직접 GET·Next.js 경유 GET에서 모두 빈 목록이었다. 메일 규칙의 revision·mode·enabled 값은 일치했고 세션은 HTTP 200 로그아웃으로 종료했다. 실제 항목이 있는 계정의 변환·읽기 권한·편집은 미검증이다.
- 실제 계정의 `GET /api/mail/compose`는 발송 없이 HTTP 200으로 기본 발신자·사용 가능한 발신자 목록·서명·양수 첨부 한도를 반환했다. 기본 발신자는 사용 가능 목록에 포함됐고, 임시 세션은 HTTP 200 로그아웃했다. 이는 작성 옵션의 읽기 검증이며 초안 저장·업로드·발송 성공을 증명하지 않는다.
- 같은 계정의 로컬 Next.js 경유 읽기 API에서 연락처·결재·공용 편지함·메일 규칙·보안·환경설정, 2026년 9월 일정, 첨부 있는 메일 검색, 격리 목록의 GET이 각각 HTTP 200을 반환했다. 이는 인증·라우팅·응답 성공 확인이며 각 화면의 데이터 내용 일치나 변경 기능 검증은 아니다.
- 유효하지 않은 테스트 쿠키로 `/api/mail/session`은 401, `/ko`와 `/ko/settings`는 로그인 경로로 307 이동, `/ko/login`은 200을 확인했다. 이 검증은 만료된 실제 토큰과 서버 장애 복구 사례를 대체하지 않는다.
- 인증된 검증 세션으로 10개 locale(`ko`, `en`, `de`, `es`, `fr`, `it`, `pt`, `ja`, `zh`, `zh-hant`) 각각의 홈·캘린더·설정 경로가 모두 HTTP 200으로 서버 렌더링되는 것을 확인했다. 번역 문구의 정확성, 클라이언트 hydration, 반응형 레이아웃까지 확인한 것은 아니다.
- 실제 브라우저에서 테스트 도메인의 설정 화면을 1280px·390px·360px 너비로 확인했다. 각 너비에서 헤더와 설정 카드가 겹치지 않았고 문서 가로 스크롤이 없으며 콘솔 오류가 0건이었다. 로컬 익명 로그인 화면도 390px에서 가로 스크롤·콘솔 오류가 없고, MFA 요구 전의 단정적 안내가 표시되지 않음을 확인했다. 이는 다른 업무 화면과 모든 locale의 시각적 회귀를 대체하지 않는다.
- 추가로 실제 브라우저의 390px에서 캘린더·주소록·결재·격리·검색·공용 편지함·규칙·파일·보안·접근성·단축키 11개 경로, 1280px에서 이들 경로와 메일 홈·설정까지 13개 경로를 탐색했다. 문서 가로 스크롤과 콘솔 오류는 없었다. `/rules`는 `/settings/filters`로 이동한다. 일부 탐색 직후의 로딩 표시는 확인했으나 각 화면의 상세 데이터 일치나 픽셀 단위 배치까지 증명한 검사는 아니다.
- 로컬 live 브라우저의 360px·390px·1280px에서 메일 홈·캘린더·주소록·검색·파일·설정 6개 경로의 업무 헤더와 본문 진입을 다시 확인했다. 18개 조합 모두 브랜드가 보였고 헤더 및 문서 가로 넘침, 화면 밖 헤더 버튼, 브라우저 오류 로그가 없었다. 이는 기본 레이아웃 회귀 확인이며 화면별 데이터 내용·동작·모든 언어를 검증한 결과는 아니다.
- 같은 로컬 live 브라우저에서 10개 언어의 메일 홈·캘린더·검색·설정 헤더를 360px와 1280px로 확인했다. 80개 경로·너비 조합에서 문서·헤더 가로 넘침, 화면 밖 헤더 버튼, 경고 화면 및 브라우저 오류 로그가 없었다. 모바일 브랜드는 헤더에, 데스크톱 브랜드는 250px 사이드바에 표시됐다. 이 검사는 헤더·라우팅의 회귀 확인이며 번역 정확성, 본문 데이터와 기능, 배포 화면까지 증명하지 않는다.

사이드바 저장 용량은 mock 모드에서는 시연 수치를 사용한다. live 모드에서는 JMAP `Mailbox/get`의 `x-tastemail-usedBytes`와 `x-tastemail-quotaBytes`가 유효할 때만 표시하며, 서버가 값을 주지 않으면 임의 수치로 대체하지 않는다. 인증된 업무 요청에서는 보호된 업무 레이아웃이 메일함 요약을 먼저 읽어 SSR 첫 화면에 용량을 포함한다. 로그인·설치 화면까지 공유하는 상위 locale 레이아웃에서는 이 조회를 하지 않아, 업무 화면 진입 시 이전 익명 레이아웃의 빈 초기값을 재사용하지 않는다. CSR은 목록 응답 및 60초 간격 요약으로 갱신한다. 갱신 중과 일시적인 메일 목록·요약 실패 및 수동 재시도 중에는 마지막으로 확인한 수치를 유지하면서 오류와 재시도를 표시한다. 요약 실패 후에도 60초 간격으로 다시 확인한다. 인증·권한이 거부되면 보관한 수치를 비운다. 첫 SSR 요약 요청 자체가 실패하면 확인된 수치가 없으므로 임의 수치를 표시하지 않는다. 합성 API 계약에서 인증된 설정 화면과 받은편지함의 첫 HTML에 실제 요약이 포함되는 것을 확인했다. 로컬 인증 브라우저에서는 새로고침 직후와 설정 화면 이동·뒤로 복귀 후에도 받은편지함 용량 표시가 유지됨을 확인했다. 테스트 도메인의 새 계정 설정 탭에서도 설정 본문이 로딩 중인 첫 접근성 상태에 받은편지함 용량 `3.2 MiB / 20 GiB`가 이미 보였다. 이는 배포 화면의 조기 표시 관찰이며 HTML 원문·첫 페인트의 픽셀 시점이나 갱신 실패·수동 재시도 동작은 증명하지 않는다.

공통 헤더의 live 프로필도 이 SSR 메일함 요약의 계정 이름을 사용한다. CSR 요약을 다시 읽을 때 이름을 함께 갱신하므로 별도 `/api/mail/session` 호출 없이 같은 계정을 표시한다. 인증·권한 실패 시에는 보관한 이름을 지운다. 합성 계약과 로컬 렌더링은 확인할 수 있지만 배포 화면의 첫 페인트와 다른 계정으로 재로그인한 경우는 아직 미검증이다.

개인 계정의 역할 없는 사용자 지정 편지함은 live 사이드바에 서버 이름·읽지 않은 수와 함께 표시하며, 선택 시 서버가 반환한 편지함 ID에 한정해 `Email/query`·`Email/get`으로 목록을 읽는다. live 검색의 편지함 필터에서도 이 ID를 선택할 수 있으며, 서버는 현재 개인 계정의 역할 없는 편지함인지 다시 확인한다. 데스크톱 읽기 창의 이동 메뉴와 모바일 메일 목록의 이동 시트에서 시스템↔사용자 지정 편지함 및 사용자 지정 편지함 간 이동을 제공한다. 사용자 지정 편지함에서 옮길 때는 현재 선택된 출발 편지함 소속만 제거하고 다른 사용자 지정 편지함 소속은 보존한다. 편지함 생성·이름 변경·삭제에는 별도의 Rust HTTP/JMAP 계약이 필요하다. 실제 배포 계정으로 사용자 지정 편지함 변경은 검증하지 않았다.

메일 외 업무 화면으로 직접 진입해도 live 사이드바의 메일함 수치가 비어 있지 않도록, `/api/mail/mailboxes`가 인증된 JMAP 세션과 `Mailbox/get`의 요약만 조회한다. 이 경로는 메일 본문을 읽지 않으며 세션 만료·권한 부족·요청 제한·서버 장애를 구분해 사이드바 오류와 재시도에 전달한다. 테스트 도메인의 실제 계정에서 `/ko/calendar`로 이동한 후에도 받은편지함·보낸편지함의 용량과 읽지 않은 수가 표시되는 것을 확인했다. 세션 만료·오류 복구는 검증하지 않았다.

업무 공통 레이아웃의 메일함 요약은 현재 계정의 컨텍스트에 보관한다. 요약을 이미 성공적으로 읽은 상태에서 캘린더·설정 등 페이지 경로만 변경하면 같은 요약을 즉시 다시 요청하지 않는다. 메일 외 화면에 머무는 동안 성공한 요약은 60초 후 재조회하고, 새로고침·명시적 재시도·메일 변경으로 조회 세대가 바뀐 경우에도 다시 읽는다. 오류가 난 요약은 무한 자동 재시도하지 않고 수동 재시도 상태를 유지한다. 이 요청 정책은 코드 수준 변경이며 실제 브라우저 네트워크 기록으로는 아직 계측하지 않았다.

업무 셸의 초기 인증 표시는 서버 레이아웃이 이미 확인한 세션 결과를 사용한다. 클라이언트에서 첫 렌더 직후 동일한 `/api/mail/session`을 다시 요청하며 화면을 로딩 상태로 가리던 동작을 제거했다. App Router가 서버 레이아웃을 재사용하는 이후의 업무 경로 이동에서는 매번 세션을 재검사하고, 같은 경로에 머무는 동안에는 60초 경과 후 창 복귀·주기 타이머가 재검사한다. 모든 `/api/mail` 요청은 계속 서버에서 개별 인증한다. 로컬 인증 브라우저에서 캘린더 직접 진입 직후 공통 셸이 보이고 일정 데이터만 로딩되는 상태, 설정으로 이동할 때 셸이 유지되는 상태를 확인했다. 후속 경로 재검사 변경의 ESLint·TypeScript·프로덕션 빌드는 통과했다. 배포 화면의 초기 깜빡임·실제 세션 만료 전환·네트워크 요청 횟수는 아직 계측하지 않았다.

후속 세션 표시 보정: 업무 경로가 바뀌면 새 경로의 세션 확인이 성공할 때까지 콘텐츠를 로딩 상태로 가린다. 60초 주기·창 복귀 재확인 중에도 기존 콘텐츠를 가리고, 성공하면 다시 표시한다. 서버의 모든 API 인증은 그대로 유지한다. 변경 컴포넌트의 ESLint·TypeScript와 변경 입력의 프로덕션 빌드는 통과했고, 로컬 인증 브라우저에서 받은편지함→캘린더→설정→받은편지함 이동 후 각 화면 제목이 표시되는 것을 확인했다. 이는 정상 세션 경로 이동 확인이며 실제 만료 세션·401·일시적 장애의 브라우저 전환은 아직 검증하지 않았다.

주소록 변경 오류 안내: live 연락처 저장·삭제의 `invalid_request`와 `not_found`를 일반 서버 장애와 구분해 각각 입력 확인 및 목록 재확인으로 안내한다. 10개 언어 키 검사, 변경 컴포넌트 ESLint, TypeScript 검사는 통과했다. 실제 서버에서 400·404를 발생시키는 변경 요청은 수행하지 않았다.

live 전역 검색은 검색어가 없을 때 `Email/query`의 전체 메일 결과를 페이지 단위로 표시하고, 검색어가 있으면 JMAP `text` 조건과 날짜순 페이지 이동을 연결한다. `from:`, `to:`, `cc:`, `bcc:`, `subject:`, `body:`, `filename:`, `in:`, `has:attachment`, `is:unread`, `is:read`, `is:starred`, `larger:`, `smaller:` 검색 문법은 Rust 서버의 `Email/query` 필터로 변환하고, 따옴표로 묶은 단일 문구에서는 따옴표를 제거한 검색어를 전달한다. 크기는 바이트 또는 `kb`·`mb`·`gb`를 받아 기존 TASTEMAIL 웹메일과 동일하게 엄격한 초과·미만 경계로 처리한다. 화면의 기간·편지함·첨부 있음 필터도 `after`·`inMailbox`·`hasAttachment` 조건으로 서버에 전달한다. 펼친 메일 결과의 첨부 파일명은 인증된 Next.js 다운로드 경로로 연결한다. 별도 테스트 계정의 브라우저에서 `has:attachment` 결과 3건과 펼친 결과의 같은 출처 다운로드 링크 1개를 확인했다. 같은 별도 테스트 계정에서 `filename:live-upload-smoke.txt` 검색 결과 1건을 열어 인증 프록시의 첨부 링크로 파일을 내려받았고, 저장된 117바이트 파일의 SHA-256이 업로드 원본과 일치했다. 테스트 도메인에서 `larger:1b subject:"GXWebMail integration test"`는 해당 자체 수신 메일 1건을 반환했다. 같은 계정에서 `smaller:1gb subject:"GXWebMail integration test"`는 1건, `smaller:1b subject:"GXWebMail integration test"`는 0건이었다. 이는 특정 메일 한 건에 대한 크기 문법의 양성·음성 사례이며 정확한 크기 경계값과 여러 단위 조합은 아직 검증하지 않았다. mock 검색 화면의 사람·독립 파일 결과와 첨부 유형·라벨 필터는 여전히 live 화면에 적용되지 않는다. 사람·독립 파일 결과는 전용 서버 데이터 계약이 없고, 첨부 MIME 유형 및 mock 라벨의 서버 대응도 확인되지 않았다. 반면 `Email/query`가 이미 지원하는 메일 본문·주소·키워드·첨부 파일명 등은 위 검색 문법으로 프런트엔드에 연결됐다. 미지원 계약과 미연동 검색 UI를 같은 상태로 취급하지 않는다.

`in:` 문법은 서버 메일함 이름이 영어여도 한국어 기본 메일함 별칭(받은편지함·임시보관함·보낸편지함·보관함·스팸·휴지통)을 현재 계정의 역할 ID에 연결한다. `from:`처럼 지원하는 필터의 값이 비었거나 `has:unknown`이면 일반 텍스트 검색으로 넓히지 않고 `400 invalid_request`를 반환한다. 단위 검사와 새 빌드의 합성 Next.js/JMAP 계약 검사가 통과했다. 테스트 도메인의 별도 계정에서 `in:받은편지함 subject:"GXWebMail integration test"`가 해당 받은 메일 1건을 반환하고, `has:unknown`은 결과 목록 대신 잘못된 검색어 안내를 표시하는 것을 확인했다. 다른 한국어 별칭·빈 필터 값·직접 API 응답 상태 코드는 실계정에서 미검증이다.

날짜 검색식 `after:`·`before:`도 Rust `Email/query`의 동명 필터로 변환한다. `YYYY-MM-DD`는 UTC 자정(`T00:00:00Z`)으로, RFC 3339 시각은 지정한 시간대 그대로 전달한다. 잘못된 날짜·빈 값은 검색 범위를 넓히지 않고 거절한다. 서버는 각각 수신 시각의 엄격한 초과(`after`)·미만(`before`)을 적용한다. 단위 검사, 변경 파일 ESLint, 프로덕션 빌드와 합성 Next.js/JMAP 계약 검사는 통과했으나 실제 계정의 날짜 경계 결과는 아직 검증하지 않았다.

테스트 도메인의 기존 로그인 세션에서 폴더 필터를 `전체`로 둔 채 `in:보낸편지함 GXWebMail integration test`를 검색해 승인된 자기 수신 메일 1건이 반환됨을 확인했다. 이는 기존에도 지원한 `보낸편지함` 별칭의 실제 계정 확인이며, 새로 추가한 임시보관함·보관함·휴지통 한국어 별칭의 실제 결과를 검증한 것은 아니다. 처음에는 열린 탭에 영어 `Inbox` 배지가 남아 있었지만, 페이지 새로고침 뒤 기존 검색어의 배지가 `받은편지함`으로 표시됐다. 서버 데이터는 변경하지 않았다.

같은 테스트 계정의 새로고침된 화면에서 폴더 선택은 `전체`인데 검색식에 `in:보낸편지함`을 넣으면 결과는 1건이나 배지는 `받은편지함`인 것을 확인했다. 메일이 두 메일함에 속해 첫 번째 소속이 선택되는 문제이므로, 검색식의 명시적 `in:` 조건도 선택한 폴더 필터와 같이 결과 배지에 우선 반영하도록 변환했다. 새 빌드의 합성 계약에서는 받은편지함과 사용자 지정 편지함에 동시에 속한 메일을 `in:Project`로 검색할 때 `Project`를 반환함을 확인했다.

2026-09-29 테스트 도메인의 인증된 화면에서 `in:보낸편지함 GXWebMail attachment integration test`를 직접 열어, 검색 결과 1건의 배지가 `보낸편지함`으로 표시되는 것을 확인했다. 해당 메일은 받은편지함에도 있는 자기 수신 메일이다. 이는 배포 화면에서 검색식의 명시적 편지함 우선 표시를 확인한 것으로, 다른 편지함이나 사용자 지정 편지함의 모든 조합을 검증한 것은 아니다.

검색 화면의 live 편지함 필터에는 받은편지함·임시보관함·보낸편지함·보관함·스팸·휴지통과 서버가 반환한 사용자 지정 편지함을 제공한다. 스팸 선택은 JMAP의 `junk` 역할 메일함 ID로 변환한다. 합성 어댑터 계약에서 임시보관함·스팸·휴지통의 ID 조건을 확인했고, 실제 테스트 도메인 계정의 브라우저에서는 전체 7건에서 스팸 1건, 휴지통 0건, 임시보관함 0건으로 각각 좁혀지는 것과 전체 7건으로 복구되는 것을 확인했다. 검색 결과의 내용을 다른 서버 클라이언트와 대조한 검증은 아니다.

live 검색 정렬은 Rust `Email/query`가 실제로 허용하는 단일 `receivedAt` 비교자의 내림차순(최신순)·오름차순(오래된순)만 제공한다. JMAP 세션의 `emailQuerySortOptions`에는 `sentAt`, `size`, `from`, `to`, `subject`도 광고되지만 현재 Rust `email_query_sort`는 이 속성을 `unsupportedSort`로 거부한다. 따라서 mock 검색의 관련도순·보낸사람순을 live 기능으로 노출하지 않는다. 합성 계약에서 `sort=oldest`의 `isAscending: true`와 미지원 정렬 요청의 HTTP 400을 확인했다. 실제 테스트 도메인의 전체 7건에서 최신순 첫 항목의 시각은 당일 08:13, 오래된순 첫 항목은 9월 26일이었고 끝 항목도 반대로 바뀌었다. 기본 최신순으로 복구했다. 360px 화면에서도 검색 제목과 정렬 선택이 겹치지 않았고 문서 가로 스크롤이 없었으며 임시 뷰포트 설정을 해제했다.

검색 필터 한도: Rust `Email/query`는 필터 노드 64개와 검색 텍스트 256자를 제한한다. GXWebMail은 화면 필터에 필요한 노드를 남겨 두고 문법 조건 56개 초과 또는 제어 문자 포함 검색을 `400 invalid_request`로 구분한다. 조건이 많은 검색식을 조용히 일반 텍스트 검색으로 바꾸지 않는다.

로그인·메일 읽기·검색의 live 응답은 인증 실패(401), 권한 부족(403), 요청 제한(429), 일시적 서버 장애(5xx)를 서로 다른 상태로 전달한다. JMAP 메서드 응답 자체가 오류인 경우 Rust 소스의 `forbidden`·`accountNotFound`를 권한 부족, `rateLimit`을 요청 제한, `serverFail`을 재시도 가능한 장애로 구분한다. `Email/set`의 개별 `notUpdated`에서도 `serverFail`을 재시도 가능한 장애로 전달한다. 합성 루프백 검증은 통과했지만 실제 배포 서버의 정책·제한값은 검증하지 않았다. 메일 로드 실패 시 이전 목록·용량·읽지 않음 수를 현재 결과처럼 표시하지 않으며, 메일함 요약 상태에도 같은 오류를 기록해 다른 업무 화면에서 빈 수치가 정상 0건으로 보이지 않게 한다.

`Email/set.ifInState`는 Rust 메서드 디스패치 시점의 계정 상태와 비교되고, 불일치하면 쓰기 전에 `stateMismatch`로 거부된다. GXWebMail은 이를 결과 불명인 503과 구분해 409 `conflict`로 전달한다. 개인 메일함 이동은 최신 메일함 소속과 상태를 다시 읽어 한 번만 재시도하며, 재차 충돌하면 409를 표시한다. 공용 메일 이동·영구 삭제는 자동 재시도 없이 409를 표시하고 목록을 다시 읽는다. 응답 중단·5xx처럼 변경 결과가 불명확한 경우에만 즉시 재시도를 잠근다. 실제 어댑터 소스를 합성 응답으로 실행하는 단위 검사에서 한 번의 충돌 후 성공, 두 번의 충돌 후 중단, `serverFail` 비재시도를 확인했다. 합성 루프백의 충돌 시나리오 예상값도 갱신했지만 현재 소스로 재빌드한 통합 검사는 아직 실행하지 않았다. 실제 서버에서의 동시 변경 경합과 상태 비교·저장의 원자성도 검증하지 않았다.


live 변경 API는 메일 상태 변경·이동뿐 아니라 연락처·일정·결재·규칙·환경설정·세션 해제 요청도 `Origin`이 없거나 현재 웹메일 출처와 일치하지 않으면 요청 본문을 처리하기 전에 거부한다. 브라우저의 같은 출처 요청은 허용하며, 무인증 읽기 API는 이 제한의 대상이 아니다. 2026-09-29 변경 빌드와 합성 루프백 계약 검사에서 Origin 없는 메일 플래그·이동·연락처 변경 요청의 403, 기존 같은 출처 변경 경로를 확인했다. 실제 배포 계정의 변경 결과는 이 검사가 대신하지 않는다.

메일 셸의 브라우저 요청도 제한 시간을 둔다. 목록은 45초, 업무 화면 사이드바의 메일함 요약은 25초, 읽음·별표·이동 요청은 45초가 지나면 재시도 가능한 오류로 처리한다. 전역 검색과 첨부 파일 검색은 각각 45초, 공용 편지함 목록은 25초, 공용 메일 목록은 45초가 지나면 재시도 가능한 오류로 처리한다. 화면 전환에 따른 취소와 시간 초과를 구별하며, 상태 변경 요청의 결과가 불명확하면 목록을 다시 읽는다. 이는 Rust 응답 뒤 연결이 끊긴 경우를 포함한 실제 계정 장애 시나리오의 검증을 대체하지 않는다.

1. GXWebMail Next.js를 API와 같은 호스트에서 실행해 서버 전용 `127.0.0.1:7531` 경로를 사용하거나, 인증 정보를 보호하는 별도 전송 경로를 확정한다. LAN의 평문 HTTP 경로로 로그인·토큰 요청을 보내지 않는다.
2. 배포 버전이 조사한 소스와 일치하는지 확인한다.
3. 이미 확인한 실제 계정의 JMAP 세션·메일함·목록·상세와 자기 수신 발송은 재사용한다. 아직 확인되지 않은 MFA·세션 만료, 외부 전달·발송 실패, 공유 권한과 변경 실패 경계를 해당 테스트 계정·환경에서 개별 검증한다.
4. 기능마다 `지원/미지원/권한 필요/배포 미확인` 상태를 갱신한다. 실제 데이터 변경은 승인된 테스트 계정과 대상 범위에서만 검증한다.
