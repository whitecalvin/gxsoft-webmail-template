# 109 인증 실패와 PostgreSQL 장애 관찰

로그인 인계 후 소유 실행 세션52323은 살아 있었지만 실제 브라우저 요청의 POST /api/mail/session이 약10초 후503을 반환했다. 사용자 입력·비밀번호·MFA 코드·토큰을 읽거나 재전송하지 않았다. 브라우저는 로그인 UI에 머물러 있음을 입력값 없이 확인했다.

## 현재 관찰

- 첫 진단 시 프런트엔드 health200/52ms, SSH API health200/5ms, 필수 필드 없는 인증 요청422/29ms.
- 한 번의 합성 잘못된 세션 토큰 요청은401/1199ms. 실제 토큰 없음.
- 예약된 example.invalid 주소의 존재하지 않는 합성 인증 요청은 연결 실패/34ms였다. 실제 계정에 대한 재시도·변경·발송은 하지 않았다.
- 메일 서비스는 activating/auto-restart와 active/running 사이에서 변했다. NRestarts=3 관찰. 기존 세션에서도 SSH channel connection refused 관찰.
- 최근10분 메일 서비스 로그의 알려진 문자열 집계: database67, pool timed out59. 원문·DB URL·메일 내용은 출력하지 않았다.
- PostgreSQL 메타 서비스는 active/exited지만 실제 postgresql@18-main.service는 failed/failed, Result=protocol이었다. 메타 서비스 active만으로 DB 정상이라고 판정하지 않는다.
- pg_lsclusters: PostgreSQL18/main, **포트5435**, down. 정확한5435 수신 확인도 헤더만 반환해 수신이 없었다. 최초 기본5432 확인은 이 클러스터 포트를 증명하지 않으므로5435 기록을 우선한다.
- 후속 API health는HTTP000이었다. 앞선200은 당시 관찰이며 현재 정상으로 재사용하지 않는다.
- 마지막80개 PostgreSQL 로그의 허용된 오류 분류는 could not load1, could not start1이었다. 더 구체적인 로딩 대상과 시작 실패의 근본 원인은 아직 확정하지 않았다. 로그 원문·DB 내용은 수집하지 않았다.

## 결론 및 권한 경계

현재 실계정 검증은 원래 대상109의 실제 PostgreSQL 클러스터 중단과 불안정한 API 때문에 진행할 수 없다. 프런트엔드 제한 시간을 늘리거나 인증 요청을 자동 재전송해 해결됐다고 주장하지 않는다. 서버 API 소스의 인증 경로는 credentials 조회·비밀번호 검증·MFA 검증·세션 생성의 순서이나, 이는 현재 배포 바이너리/설정의 완전 일치 증거가 아니다.

모든 SSH 진단은 기존 계정·엄격한 호스트 키 검증을 사용한 읽기 전용 요청이다. DB에 SQL을 직접 질의하지 않았고 서비스 재시작·설정 변경·복구·마이그레이션·데이터 삭제·배포를 하지 않았다. DB 복구는 운영 상태를 변경하므로 사용자 승인이 필요하다. 로그인/MFA·실제 메일 데이터 일치·권한 및 전체 회귀는 미완료이며 목표는 진행 중이다.

앞선 턴은 안전한 실행 및 브라우저 인계 진행, 이번 턴은 새 로그인503·메일 서비스 재시작·PostgreSQL5435 중단 증거로 다음 조치를 바꾼 진행 턴이다. 미검증 사용자 인증이나 운영 복구를 완료로 계산하지 않는다.
